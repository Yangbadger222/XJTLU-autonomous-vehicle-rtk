## 2026.06.29

### [RTK 基础 launch 文件重映射]

#### 涉及文件

- `scripts/launch_with_logs.sh`

#### 变更内容

- 将 `rtk-basic` 的 `LAUNCH_FILE` 参数修改为 `LAUNCH_FILE="system_rtk_basic.launch.py"`（原为 `LAUNCH_FILE="um982_rtk.launch.py"`）
- 移除了 `rtk-basic` 的 `LAUNCH_PACKAGE` 参数（原为 `LAUNCH_PACKAGE="um982_rtk_driver"`）

#### 变更原因

此前 `launch_with_logs.sh` 脚本被设置为直接调用 RTK 驱动功能包中的 launch 文件，而不是主 `bringup` 功能包中的通用系统 launch 文件。此次修改实现了架构上的一致性，统一仅使用 `system_*.launch.py` 文件，从而便于后续扩展以包含其他配置和启动组件。

#### 带来影响

现在运行 `make launch rtk-basic` 会调用 `system_rtk_basic.launch.py`，而该文件内部会进一步调用原本的 `um982_rtk.launch.py`。目前，这对机器人的实际运行没有实质影响。但在代码层面上，它使得后续向 `rtk-basic` 模式中轻松添加其他启动组件（例如 URDF 机器人模型描述）变得更加方便。

## 2026.06.18

### [Corridor RTK heading bootstrap 对齐]

#### File / 文件

- `src/navigation/gps_waypoint_dispatcher/gps_waypoint_dispatcher/gps_global_aligner_node.py`
- `src/navigation/gps_waypoint_dispatcher/gps_waypoint_dispatcher/alignment_math.py`
- `src/navigation/gps_waypoint_dispatcher/test/test_alignment_math.py`
- `src/bringup/config/master_params.yaml`
- `docs-CN/knowledge/gps_planning.md`
- `docs-EN/knowledge/gps_planning.md`
- `docs-CN/known_issues.md`
- `docs-EN/known_issues.md`

#### Change / 改动

- `gps_global_aligner_node` 新增 `/heading` 订阅，启动时采稳定双天线 heading。
- bootstrap 对齐旋转改为优先使用实时 RTK heading：`theta = map_yaw - rtk_heading_enu_yaw`。
- `launch_yaw_deg` 保留为无 heading 时的 fallback，并在与 RTK heading 差异过大时记录告警。
- 新增 `alignment_math.py` 纯数学模块，覆盖 heading 约定转换、bootstrap yaw 选择和 `theta/tx/ty` 计算。
- `master_params.yaml` 增加 heading bootstrap 参数：`use_rtk_heading_for_bootstrap`、`heading_quaternion_yaw_is_compass`、启动采样数、离散度和 mismatch 告警阈值。

#### Reason / 原因

- UM982 RTK `/fix` 已能提供高精度 ENU 位置，但 Nav2 目标需要投影到 FAST-LIO 的 `map` 坐标系。
- 旧 corridor bootstrap 主要依赖 route 文件里的 `launch_yaw_deg`，一旦初始 yaw 有几度误差，远处 waypoint 会在 `map` 中产生米级横向偏移。
- 当前 UM982 `/heading` 已经表示校准后的车辆 heading，应直接参与 ENU→map 初始旋转，而不是只用于人工观察。

#### Effect / 影响

- outdoor corridor 启动时，`ENU→map` 的旋转优先由双天线 RTK heading 决定，减少因为旧 `launch_yaw_deg` 或人工朝向确认不准导致的目标投影偏差。
- 如果现场没有稳定 `/heading`，系统仍可回退到原有 route `launch_yaw_deg` 行为，不会因为 heading 缺失直接阻塞。
- 运行期仍保持 translation-only 平滑修正，避免导航中途突然旋转整条路线；多点刚体配准仍是后续更强的路线锚定方案。

#### Reason / 原因

- 现场希望优先用 C++ 准备 RTK 基础链路，减少 Python 常驻进程，并避免单独 monitor/NTRIP 进程抢同一个串口。
- UM982 双天线 heading 可能来自 THS/HPR，也可能来自 Unicore `UNIHEADINGA`，基础链路需要同时支持。
- 现场实测 `/heading` 接近正东而车头约朝南，符合右 master / 左 secondary 横向基线比车头方向少约 90 度的安装语义。
- RTK Fixed/Float 不能只依赖 `NavSatStatus`，必须保留 raw GGA/状态输出供现场判断。

#### Effect / 影响

- 下楼后可先运行 `make launch-rtk-basic`，确认 `/fix`、`/heading`、`rtk/status` 和 raw NMEA，再进入导航模式。
- fresh clone 的 Jetson 可先 `make build-rtk-basic` 完成 RTK 烟测；完整 GPS 导航模式仍按整车栈流程构建。
- 现场可用 `FYP_RTK_PARAMS_FILE=/tmp/um982_cors.yaml` 在基础烟测和 GPS 导航模式之间复用同一份不入库 CORS 参数。
- `/heading` 现在表示校准后的车辆朝向；若后续调换天线主从或改成前后安装，只需要调整 `heading_offset_deg`。
- GPS 相关导航模式默认使用 UM982 `/dev/rtk_um982`，旧 G60 路径保留为回退但不再是主入口。
- 当前 NTRIP 实现支持普通 TCP caster；如果 CORS caster 强制 TLS，需要后续增加 TLS 支持或交给接收机/4G 模块处理。

### [下位机 B 键阻尼主动刹车]

#### File / 文件

- `src/firmware/rm_c_board/Core/Src/Joystick.c`

- `docs-CN/commands.md`

- `docs-CN/hardware_spec.md`
- `docs-EN/hardware_spec.md`
- `docs-CN/known_issues.md`
- `docs-EN/known_issues.md`
- `docs-CN/knowledge/frc.md`
- `docs-EN/knowledge/frc.md`

#### Change / 改动

- 新增 `brake_flag` 和 `Active_Brake_Output()`，B 键按下后不再走 `motor_shutdown/free_flag` 失能撤力路径。
- B 键会锁定 `Vcx/Wc=0`，在 `Speed_set()` 中以 200 Hz 执行专用阻尼刹车，不再复用行驶 PID 输出。
- 阻尼刹车按 `-BRAKE_DAMPING_KP * speed_rpm` 生成反向电流，高速段保留 `BRAKE_CURRENT_LIMIT=8000`，低速段从 `BRAKE_LOW_SPEED_RPM=300` 起用 `BRAKE_LOW_SPEED_CURRENT_LIMIT=4500` 收尾，并通过 `BRAKE_CURRENT_STEP=1200` 限制每周期电流变化；`BRAKE_DAMPING_KP=12.0` 让中高速更快顶到强刹上限。
- B 键刹车锁存只在 `brake_flag == 0` 的首次触发帧初始化，持续按住 B 不再反复 `Clear_Brake_State()` 清空电流爬坡；B 急停指示去掉阻塞式 `led_pink_blink()`，改为非阻塞粉色常亮。
- 四轮进入 `BRAKE_STOP_RPM=120` 以内后清刹车状态和 PID 状态，并切回零电流输出，避免过零后继续反向拉车轮。
- X 键、KEY 和手柄断连仍保持零电流撤力语义；上行 `ctrl_mode` 在 B 主动刹车期间报告安全接管状态。
- 更新静态回归测试和中英文安全文档。

#### Reason / 原因

- 现场需求希望 B 键不是单纯失能电机，而是能主动把车辆刹停。
- 旧 B 键 PID 刹车曾因积分限幅失效和持续反向输出导致倒转；现场测试又发现普通限流 PID 刹车会产生较明显前后晃动，因此改为高速强刹、低速阻尼收尾的专用刹车曲线。
- 实车观察到 B 键触发后存在一小段先滑行再刹车，根因之一是按住 B 会反复清空刹车爬坡状态，且原粉色闪烁函数带 `HAL_Delay()` 阻塞调度。

#### Effect / 影响

- B 键现在与 X 键有明确区别：X 是撤力滑停，B 是阻尼主动刹车后零电流释放。
- B 键持续按住时应更快进入连续刹车段，避免因重复清爬坡或 LED 延时造成前段制动迟滞。
- 该行为已通过静态回归测试和本地 STM32 GCC 编译；仍必须先抬轮台架验证 B 刹车方向、刹车距离和过零释放，再做地面测试。

- 将健康聚合的 stale 判断、LIO 退化判断、PGO 修正状态、RTK 状态和底盘速度聚合逻辑抽成无 ROS 依赖的 C++ 核心头文件。

#### Reason / 原因

#### Effect / 影响

- FRC shadow/full 模式少三个 Python 常驻进程，预计可降低 Jetson 运行内存占用。

#### Change / 改动

- KEY 急停分支不再停跑后只闪灯，而是持续调用 `Emergency_Stop_Output()` 下发零电流 CAN 帧，并改为非阻塞红灯常亮。
- `Set_free;` / `led_white_start;` 无效表达式修复为函数调用，新增 `Emergency_Stop_Output()` 统一清零 `Vcx/Wc`、目标转速、PID 输出和目标。
- PS2 `B` 键从 PID 锁零速语义改为与 `X` 一致的撤力失能路径，并立即发送零电流帧。
- `pid.c` 恢复积分限幅、`last_err` 更新，并对 PID 时间步长做 1-50 ms 钳位；固件 Makefile 增加 `-Werror=unused-value`。
- 新增不依赖 ROS 的静态回归测试，锁定 KEY/B/X 停止路径与 PID 安全契约。
- 更新安全文档，明确 `X` 仍是最高优先级软件失能，红色物理急停覆盖所有软件命令，`B` 在台架/车测验证前不得替代急停。

#### Reason / 原因

- 旧 KEY 路径会设置 `stop_flag` 后停止任务调度，导致底盘 CAN 不再持续刷新，C620 可能锁存最后一帧电流。
- 旧 `Set_free;` 只是函数名表达式，不会真正调用零电流输出和 PID 清零逻辑。
- 旧 `B` 键通过 PID 锁零速主动刹车，配合未生效的积分限幅会造成过零后的反向电流输出。

#### Effect / 影响

- KEY、`X`、`B` 和手柄掉线停止路径都应进入零电流撤力滑停，而不是停发 CAN 或依赖 PID 抱死。
- 正常串口/手柄行驶路径的 PID 增益值未调整，但积分限幅现在生效；如台架发现跟踪变化，应单独评估 `IntegralLimit`，不要回滚停止路径安全修复。
- 该修复已通过静态回归测试和本地固件编译；仍必须按抬轮台架流程验证后再进行地面测试。
