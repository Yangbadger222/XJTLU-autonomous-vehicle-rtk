#### 主参数（Master Params）变更说明

* **变更理由**：在新添加的 URDF 结构中，`base_footprint` 作为根关节（root link），代表机器人在地面上的投影，而 `base_link`（物理底盘中心）则是它的子节点。如果 FAST-LIO2 的 `body_frame` 参数保持为 `base_link`（发布 `odom -> base_link`），那么 `base_link` 将拥有多个父节点：`odom`（动态发布）和 `base_footprint`（来自 URDF 的静态发布）。在 ROS TF 树中，多父节点是非法的，会导致坐标系解析崩溃。将 `body_frame` 更改为 `base_footprint` 可以生成一个合法且符合标准的链路：`odom -> base_footprint -> base_link`。
* **下游兼容性**：所有继续查询面向/来自 `base_link` 变换的下游节点（例如 `route_server`、`gps_global_aligner`、`gps_route_runner`、`goal_manager` 以及 Nav2 代价地图层）均不受影响，因为 TF 树会透明地解析该变换。
* **验证情况**：FAST-LIO2 中的高度滤波（`publish_cloud_height_filter_enabled`）直接基于 IMU 状态向量高度，该高度与 `body_frame` 字符串的配置无关，因此点云滤波仍能完全保持正确。

以下是关于此参数变更的详细剖析：

#### 1. 该参数变更影响哪些文件

* **参数源**：[master_params.yaml](/src/bringup/config/master_params.yaml) 是中央参数入口点。
* **雷达里程计（LiDAR Odometry）**：FAST-LIO2 ([lio_node.cpp](/src/perception/fastlio2/src/lio_node.cpp)) 读取该参数。它现在将动态坐标变换发布为 `odom -> base_footprint`（此前为 `odom -> base_link`），并将话题输出 `/fastlio2/body_cloud`、`/fastlio2/body_filtered` 和 `/fastlio2/lio_odom` 标记在 `base_footprint` 下。
* **点云转激光扫描（Pointcloud to Laserscan）**：[pointcloud_to_laserscan_node](/src/bringup/launch/system_slam.launch.py%23L64-L74) 订阅了 `/fastlio2/body_cloud`。由于其 `target_frame` 参数为空（`""`），它会继承输入点云的坐标系 ID（frame ID）。因此，现在发布的 `/scan` 话题带有 `header.frame_id = base_footprint`。
* **下游消费者**：订阅 `/scan` 的节点（如 Nav2 代价地图和 SLAM Toolbox）会查询从 `base_footprint` 到其参考坐标系（`odom`/`map`）的 TF 变换。

#### 2. 是否有可能破坏任何现有功能

**不会，它不会破坏任何现有功能。**

* **TF 连通性**：尽管像 `route_server`、`gps_global_aligner_node.py` 和 `gps_route_runner_node.py` 这样的节点会查询相对于 `base_link` 的变换，但 TF 树依然保持连续。因为 `base_footprint` 和 `base_link` 通过静态变换连接，TF 会动态且透明地解析从 `map`/`odom` 到 `base_link` 的查询。
* **2D 导航/对齐**：base.urdf.xacro 中 `base_footprint` 与 `base_link` 之间的平移纯粹是垂直方向的（$Z \approx 22.9\text{ cm}$，且 $X=0, Y=0, \text{yaw}=0$）。由于 2D 路径规划、对齐和导航节点仅使用 $XY$ 坐标和 $\text{yaw}$ 航向角，因此它们接收到的物理值是完全相同的。
* **点云 Z 轴滤波**：FAST-LIO2 的点云高度滤波（`publish_cloud_height_filter_enabled`）使用 IMU 状态向量的估计高度 `m_kf->x().t_wi.z()` 来计算相对高度，这与 `body_frame` 的字符串配置无关。点云滤波依然完全正确。

#### 3. 新的 TF 树结构如何，以及是否被正确遵循

现在，`robot_state_publisher` 已在所有激活的启动模式中成功加载了 URDF。生成的 TF 树布局如下：

* **无全局地图（基础 / SLAM / 探索 模式）**

```mermaid
graph TD
    odom[odom (FAST-LIO2 世界坐标系)] -->|动态变换| base_footprint[base_footprint (地面投影)]
    base_footprint -->|URDF 静态: base_joint| base_link[base_link (底盘中心)]
    base_link -->|URDF 静态| laser_link[laser_link (激光雷达)]
    base_link -->|URDF 静态| imu_link[imu_link (IMU)]
    base_link -->|URDF 静态| camera_link[camera_link (相机)]
    base_link -->|URDF 静态| wheels[车轮 & 万向轮]
```

* **有全局地图（GPS 导航 / PGO 模式）**

```mermaid
graph TD
    map[map (全局地图坐标系)] -->|动态变换 (PGO)| odom[odom]
    odom -->|动态变换| base_footprint[base_footprint]
    base_footprint -->|URDF 静态| base_link[base_link]
    base_link -->|URDF 静态| links[laser_link / imu_link / camera_link / 车轮]
```

该树被 ROS 2 环境完全遵循，因为它构建了一个从根坐标系（`map` 或 `odom`）一直延伸到叶子节点的、清晰的单父节点树。

#### 4. 我们应该针对该变更可能引发问题的边界情况进行测试吗

* **边界情况 1：独立传感器/里程计测试**：
如果开发人员单独运行 FAST-LIO2（例如 `ros2 launch fastlio2 lio_no_rviz.py`）而没有启动 URDF 节点（`robot_description.launch.py`），则 TF 树将止于 `base_footprint`。任何期待 `base_link` 的下游节点都将发生超时。
*建议*：如果下游模块处于激活状态，在手动测试期间务必将 URDF 发布器与 FAST-LIO2 一同运行。
* **边界情况 2：垂直可视化偏移（“悬空机器人”）**：
FAST-LIO2 使用 IMU 的估计位置来发布 `odom -> base_footprint`（该位置在状态向量中的初始高度为 $Z=0$，但在物理上位于地面上方约 $\approx 30\text{ cm}$ 的激光雷达高度处）。
在 URDF 中，`base_link` 位于 `base_footprint` 上方 $22.9\text{ cm}$ 处，而激光雷达位于 `base_link` 上方 $7\text{ cm}$ 处。
结果导致：
* 在物理世界中，激光雷达位于地面上方 $\approx 30\text{ cm}$ 处。
* 在 TF 树中，激光雷达位于 `base_footprint`（处于 IMU 高度）上方 $29.9\text{ cm}$ 处。
这会导致一个视觉上的伪影：在 RViz/Foxglove 中，机器人的物理模型（底盘/车轮）看起来稍微悬空在点云地面点上方。这纯粹是视觉层面的，并不会影响 2D 导航，但这是将通用 LIO 与自定义 URDF 坐标系结合使用时的一个已知伪影。


#### 5. 鉴于该分支中新添加了 URDF，该变更是合理的吗

**是的，这次变更是 100% 合理且必要的。**
如果 `body_frame` 保持为 `base_link`：

1. `robot_state_publisher` 将发布静态变换 `base_footprint -> base_link`。
2. FAST-LIO2 将发布 `odom -> base_link`。
3. 这意味着 `base_link` 将拥有多个父坐标系（`base_footprint` 和 `odom`），这在 ROS TF 库中是非法的。它会导致严重的抖动、错误以及 TF 树完整性的丧失。

将 `base_footprint` 作为动态里程计变换的目标是移动机器人的标准 ROS 惯例，这样能提供一个干净、合规的坐标树。

- Nav2 goal checker 的旧状态/到点锁存不再能让远距离 corridor subgoal 立即完成。
