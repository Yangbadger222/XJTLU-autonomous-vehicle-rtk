#### Change

- Added `brake_flag` and `Active_Brake_Output()`, so pressing `B` no longer follows the `motor_shutdown/free_flag` coast-disable path.
- `B` now locks `Vcx/Wc=0` and runs a dedicated damped-braking output from `Speed_set()` at 200 Hz instead of reusing the drive PID output.
- Damped braking generates current from `-BRAKE_DAMPING_KP * speed_rpm`, preserves `BRAKE_CURRENT_LIMIT=8000` at higher speed, tapers only below `BRAKE_LOW_SPEED_RPM=300` with `BRAKE_LOW_SPEED_CURRENT_LIMIT=4500`, and limits each-cycle current changes with `BRAKE_CURRENT_STEP=1200`; `BRAKE_DAMPING_KP=12.0` reaches the strong-brake limit sooner at medium and high speed.

- `X`, KEY, and gamepad-loss paths still use zero-current coast-stop semantics; the upstream `ctrl_mode` reports a safety takeover while `B` active braking is latched.
- Updated the static regression test and bilingual safety documentation.

#### Reason

- Vehicle-side operation needs `B` to actively stop the chassis instead of only disabling motor output.
- The old `B` PID-brake path previously caused reversal because integral limiting was ineffective and reverse current continued after zero-speed crossing; field testing then showed that the ordinary limited-PID brake still produced noticeable fore-aft oscillation, so `B` now uses a dedicated curve with strong high-speed braking and damped low-speed finishing.
- On-vehicle testing still showed a short coast-before-brake delay; one root cause was repeated ramp-state clearing while `B` was held, plus the old pink blink function blocking scheduling through `HAL_Delay()`.

#### Effect

- `B` now differs from `X`: `X` is coast-disable, while `B` is damped active braking followed by zero-current release near stop.
- Holding `B` should now enter the continuous braking phase sooner, avoiding front-end braking latency from repeated ramp resets or LED delay.
- This behavior passed the static regression test and local STM32 GCC compilation; wheel-off bench validation is still required before ground testing.

### [Lower-Controller Stop-Path Wheel-Reversal Fix]

- `src/firmware/rm_c_board/Core/Inc/Motor_Speed_pid.h`

- `docs-CN/commands.md`
- `docs-EN/commands.md`

- `docs-EN/known_issues.md`

#### Change

- Changed the KEY stop branch from task shutdown plus blocking LED blink to sustained `Emergency_Stop_Output()` zero-current CAN output with a non-blocking solid red LED.
- Replaced invalid `Set_free;` / `led_white_start;` expressions with real function calls, and added `Emergency_Stop_Output()` to clear `Vcx/Wc`, target wheel speeds, PID outputs, and PID targets.
- Changed PS2 `B` from PID zero-speed braking to the same coast-stop disable path as `X`, with immediate zero-current output.
- Restored PID integral limiting and `last_err` updates, clamped PID step time to 1-50 ms, and added `-Werror=unused-value` to the firmware Makefile.
- Added a ROS-free static regression test for the KEY/B/X stop paths and PID safety contract.
- Updated safety docs to state that `X` remains the highest-priority software disable, the red physical e-stop overrides all software commands, and `B` must not replace those stops before bench and vehicle validation.

#### Reason

- The old `Set_free;` statements only evaluated a function name expression; they did not send zero current or clear PID state.

#### Effect

- KEY, `X`, `B`, and gamepad-loss stop paths should now enter zero-current coast stop instead of stopping CAN output or relying on PID braking.
- Normal serial/gamepad driving PID gains are unchanged, but integral limiting is now active; if bench testing shows tracking changes, evaluate `IntegralLimit` separately instead of reverting the stop-path safety fix.
