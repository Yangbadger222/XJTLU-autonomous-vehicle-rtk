### [RTK Authority map_base Jump-Gate Offline Validation]

#### File

- `src/navigation/gps_waypoint_dispatcher/gps_waypoint_dispatcher/rtk_authority.py`
- `src/navigation/gps_waypoint_dispatcher/gps_waypoint_dispatcher/rtk_map_odom_corrector_node.py`

- `docs-EN/knowledge/nav2_tuning.md`

#### Change

- Added `compute_authority_target_delta()`, binding authority target-jump translation/yaw checks to raw RTK `map_base` instead of raw `map->odom` target.
- Added `_last_raw_map_base` to `rtk_map_odom_corrector`; the node records the last trusted raw RTK `map_base` after each normal publish.
- Kept raw `map->odom` target low-pass filtering, per-step limiting, and raw/output gap diagnostics for the actual published `map->odom`.
- Added a unit test for the case where raw RTK `map_base` moves only about `0.32m`, but raw `map->odom` target translation exceeds `6m` because the vehicle is about `67m` from the odom origin and yaw changes.

#### Reason

- Offline replay across 6 corridor bags on the Linux analysis machine showed the old `map->odom` target gate would reject hundreds of samples in bags such as `2026-07-09-14-23-47`, `15-45-27`, and `17-55-23`; at the same time, raw RTK `map_base` max step stayed around `0.20-0.36m`, so RTK vehicle position was not truly jumping by meters.
- The root cause is `map->odom = map_base * inverse(odom_base)`: when the vehicle is tens of meters from the odom origin, a few degrees of yaw correction can amplify raw `map->odom` target translation into the tens of meters, which does not mean the RTK vehicle pose jumped.

#### Effect

- The 17:55-style failure where RTK `map_base` is smooth but authority freezes in long `TARGET_JUMP` windows should be removed; offline replay of all 6 bags produced `0` rejects with the new map_base gate.
- `map->odom` still releases through the existing low-pass filter and `max_base_yaw_step_m` limiter, so the amplified target is not published into TF in one step.

#### Master Params Change Explanation

- **Justification**: In the newly added URDF structure, `base_footprint` acts as the root link representing the ground projection of the robot, while `base_link` (the physical chassis center) is its child. If FAST-LIO2's `body_frame` parameter remained `base_link` (publishing `odom -> base_link`), `base_link` would have multiple parents: `odom` (dynamic) and `base_footprint` (static from URDF). In ROS TF trees, multiple parents are illegal and break frame resolution. Changing the `body_frame` to `base_footprint` produces a valid and standard chain: `odom -> base_footprint -> base_link`.
- **Downstream Compatibility**: All downstream nodes (such as `route_server`, `gps_global_aligner`, `gps_route_runner`, `goal_manager`, and Nav2 costmap layers) that continue to query transforms to/from `base_link` are unaffected because the TF tree resolves the transform transparently.
- **Verification**: Height filtering in FAST-LIO2 (`publish_cloud_height_filter_enabled`) is based directly on the IMU state vector height, which is independent of the `body_frame` string configuration, keeping point cloud filtering fully correct.

A detailed breakdown of the parameter change is written below:


#### 1. Which files this parameter change affects
* **Parameter Source**: [master_params.yaml](/src/bringup/config/master_params.yaml) is the central parameter entry point.
* **LiDAR Odometry**: FAST-LIO2 ([lio_node.cpp](/src/perception/fastlio2/src/lio_node.cpp)) reads this parameter. It now publishes the dynamic coordinate transformation as `odom -> base_footprint` (previously `odom -> base_link`) and tags the topic outputs `/fastlio2/body_cloud`, `/fastlio2/body_filtered`, and `/fastlio2/lio_odom` under `base_footprint`.
* **Pointcloud to Laserscan**: The [pointcloud_to_laserscan_node](/src/bringup/launch/system_slam.launch.py#L64-L74) subscribes to `/fastlio2/body_cloud`. Since its `target_frame` parameter is empty (`""`), it inherits the frame ID of the input cloud. Thus, `/scan` is now published with `header.frame_id = base_footprint`.
* **Downstream Consumers**: Nodes subscribing to `/scan` (such as Nav2 costmaps and SLAM Toolbox) query TF transforms from `base_footprint` to their reference frames (`odom`/`map`).


#### 2. Whether it would potentially break any existing function
**No, it will not break any existing functionality.**
* **TF Connectivity**: Even though nodes like `route_server`, `gps_global_aligner_node.py`, and `gps_route_runner_node.py` query transforms relative to `base_link`, the TF tree remains continuous. Because `base_footprint` and `base_link` are connected via a static transform, TF dynamically and transparently resolves queries from `map`/`odom` to `base_link`.
* **2D Navigation/Alignment**: The translation between `base_footprint` and `base_link` in [base.urdf.xacro](file:///Ubuntu-22.04/home/yoonzh22/robotrepo/XJTLU-autonomous-vehicle-rtk/src/bringup/urdf/rosbot/base.urdf.xacro#L107-L111) is purely vertical ($Z \approx 22.9\text{ cm}$, with $X=0, Y=0, \text{yaw}=0$). Because 2D path planning, alignment, and navigation nodes only use the $XY$ coordinates and $\text{yaw}$ heading, they receive identical physical values.
* **Point Cloud Z-Filtering**: FAST-LIO2's point cloud height filtering (`publish_cloud_height_filter_enabled`) computes relative heights using the IMU state vector's estimated height `m_kf->x().t_wi.z()`, which is independent of the string configuration of `body_frame`. Point cloud filtering remains fully correct.


#### 3. How the new TF tree looks like, and if it is properly respected
The URDF is now successfully loaded by `robot_state_publisher` across all active launch modes. The resulting TF tree layout is:

- **Without Global Map (Basic / SLAM / Explore modes)**
```mermaid
graph TD
    odom[odom (FAST-LIO2 World Frame)] -->|Dynamic Transform| base_footprint[base_footprint (Ground Projection)]
    base_footprint -->|URDF Static: base_joint| base_link[base_link (Chassis Center)]
    base_link -->|URDF Static| laser_link[laser_link (LiDAR)]
    base_link -->|URDF Static| imu_link[imu_link (IMU)]
    base_link -->|URDF Static| camera_link[camera_link]
    base_link -->|URDF Static| wheels[Wheels & Casters]
```

- **With Global Map (GPS Navigation / PGO modes)**
```mermaid
graph TD
    map[map (Global Map Frame)] -->|Dynamic Transform (PGO)| odom[odom]
    odom -->|Dynamic Transform| base_footprint[base_footprint]
    base_footprint -->|URDF Static| base_link[base_link]
    base_link -->|URDF Static| links[laser_link / imu_link / camera_link / wheels]
```

This tree is fully respected by the ROS 2 environment because it forms a clean, single-parent tree from the root frame (`map` or `odom`) down to the leaves.

#### 4. Whether we should test for any edge case that may be problematic because of the change
* **Edge Case 1: Standalone Sensor/Odometry Tests**:
  If a developer runs FAST-LIO2 alone (e.g., `ros2 launch fastlio2 lio_no_rviz.py`) without launching the URDF node (`robot_description.launch.py`), the TF tree will stop at `base_footprint`. Any downstream node expecting `base_link` will time out. 
  *Recommendation*: Always run URDF publisher alongside FAST-LIO2 during manual tests if downstream modules are active.
* **Edge Case 2: Vertical Visualization Offset ("Floating Robot")**:
  FAST-LIO2 publishes `odom -> base_footprint` using the IMU's estimated position (which starts at height $Z=0$ in the state vector but is physically located at the LiDAR height $\approx 30\text{ cm}$ above the ground). 
  In the URDF, `base_link` is $22.9\text{ cm}$ above `base_footprint`, and the LiDAR is $7\text{ cm}$ above `base_link`.
  As a result:
  * In the physical world, the LiDAR is $\approx 30\text{ cm}$ above the ground.
  * In the TF tree, the LiDAR is $29.9\text{ cm}$ above `base_footprint` (which is at the IMU height).
  This causes a visual artifact where the robot's physical model (chassis/wheels) appears to float slightly above the point cloud ground points in RViz/Foxglove. This is purely visual and does not affect 2D navigation, but is a known artifact of using generic LIOs with custom URDF frames.

#### 5. Whether the change is justified, given the URDF was newly added in this branch
**Yes, the change is 100% justified and necessary.**
If `body_frame` had remained `base_link`:
1. `robot_state_publisher` would publish the static transform `base_footprint -> base_link`.
2. FAST-LIO2 would publish `odom -> base_link`.
3. This would mean `base_link` has multiple parent frames (`base_footprint` and `odom`), which is illegal in the ROS TF library. It would cause severe flickering, errors, and loss of TF tree integrity.

Making `base_footprint` the target of the dynamic odometry transform is the standard ROS convention for mobile robots, providing a clean, compliant coordinate tree.

### [Dynamic-Obstacle BLOCKED_WAIT And Automatic Resume]

#### File

- `src/navigation/gps_waypoint_dispatcher/gps_waypoint_dispatcher/{goal_manager_node,route_safety}.py`
- `src/navigation/gps_waypoint_dispatcher/test/test_{goal_manager_route_graph,route_safety}.py`
- `src/bringup/launch/system_nav_gps.launch.py`
- `src/bringup/test/test_system_nav_gps_launch.py`
- `docs-CN/{commands.md,knowledge/gps_planning.md,knowledge/nav2_tuning.md,devlog/2026-07.md}` and matching English documentation

#### Change

- Nav-gps sets MPPI `retry_attempt_limit=3`, regenerating noise and retrying local avoidance only when every sampled trajectory collides.
- When authority and LIO remain healthy, an aborted `FollowPath` no longer clears the destination. The manager enters `BLOCKED_WAIT`, keeps stop override asserted, and reruns A* from the current pose every `2s`.
- A retry reaches `BLOCKED_RECOVERED` only after LIO measures continuous translation or rotation for `3s`; persistent blockage becomes terminal only after `60s`.
- User stop, authority fault, and local-odom abort continue to preempt blocked retry and cannot be hidden by automatic resume.

#### Reason

- The final obstacle test in `2026-07-21-11-09-55` recorded `Optimizer fail to compute path` after a pedestrian blocked the route, and action status 6 was immediately converted into `FAILED` by the goal manager.
- The current Humble MPPI throws `std::runtime_error` when all trajectories fail, while controller server's `failure_tolerance=1.5s` catches only `nav2_core::PlannerException`; raising that tolerance alone therefore cannot prevent the immediate abort.
- The same bag contains two separate chassis-execution failures: `junction_334` received about `0.089rad/s` rotation for 15 seconds while LIO yaw changed only `0.02deg`; the later `math_building` failure received about `0.846m/s` during its final 15 seconds while LIO moved only `0.068m`. Neither should be attributed to obstacles or A*.

#### Effect

- A temporary pedestrian blockage first receives multiple MPPI avoidance samples. If none is feasible, the vehicle safely waits at zero velocity and automatically resumes the preserved destination after the obstacle clears.
- A permanently closed route or chassis that continuously ignores commands terminates clearly after at most 60 seconds instead of occupying the goal manager forever.
- Workstation state-machine and launch regression now cover waiting, authority gating, repeated aborts, timeout, continuous measured-motion recovery, and MPPI parameter injection. Obstacle-cloud timing still requires the next debug-profile vehicle bag for acceptance.

### [Continuous FAST-LIO Propagation and RTK Reacquisition]

#### File

- `src/navigation/gps_waypoint_dispatcher/gps_waypoint_dispatcher/{rtk_authority,rtk_map_odom_corrector_node,corridor_cmd_guard,corridor_cmd_vel_guard_node}.py`

#### Change

- Added a latched continuous `LIO_BRIDGE` state after a previously trusted RTK authority loss. It freezes the last RTK-derived `map->odom` and retains FAST-LIO's `odom->base_footprint` for map-frame navigation without a fixed time or distance cut-off.
- Added a fail-closed authority speed-limit heartbeat. Normal mode publishes a high ceiling for each mode's existing guard limit; bridge mode is capped at `0.35m/s`.
- The bridge consumes FAST-LIO's existing `/fastlio2/degeneracy` stream and immediately latches motion off for stale, regularized, low-eigenvalue, or `0.50m` / `15deg` single-step LIO failures. It may re-arm only after normal RTK authority returns.
- Stable q=4 recovery now enters `RTK_REACQUIRING`: safe backlog corrections are released while moving at `0.05m/s` and `0.5deg/s`, instead of requiring a full stop before `map->odom` can return to RTK.

#### Reason

- UM982 `q=4` `/fix` is the mature absolute-position source and remains production authority, but a transient RTK/heading degradation previously made the boolean motion gate stop Nav2 even though FAST-LIO could still provide a fresh local LiDAR/IMU pose.
- A raw-observation FGO is still shadow-only and must not be required to solve continuous RTK/LIO source switching.

#### Effect

- GPS-map A* routes, road keepout, and destinations remain in the same `map` frame through RTK gating; FAST-LIO advances only the local leg of the TF chain, then RTK smoothly reclaims global authority when its gate stabilizes.
- The vehicle does not blindly dead-reckon: a missing local heartbeat, detected LiDAR degeneracy/discontinuity, or global-correction fault remains a stop condition. Unit and launch regression coverage verify continuous coasting, health gating, online reacquisition, and the speed guard contract.
